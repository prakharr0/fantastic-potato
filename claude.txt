## Root Cause Analysis

### 1. Root Cause

The crash is caused by a **`NullPointerException` in `MathEngine.recursive()`** at line 123. The `lookup` map only contains the key `100`, but `b` (the `modifier`) is almost never `100`, so `lookup.get(b)` returns `null`. The code then attempts to unbox that `null` `Integer` as a primitive `int` divisor, which throws an NPE.

### 2. Faulty Line

```java
// Line 123 — ExtremeDebugBenchmark.java
return a / divisor;  // divisor is null when b != 100
```

The `lookup` map is hardcoded with only one entry:
```java
lookup.put(100, 2);
Integer divisor = lookup.get(b);  // returns null unless b == 100
```

Since `b` is derived from `GLOBAL_COUNTER.incrementAndGet()` (values 1, 2, 3, ...), it will essentially never be `100`, so `divisor` is always `null`.

### 3. Why the Failure Happens — Step by Step

| Step | What happens |
|---|---|
| `modifier = GLOBAL_COUNTER.incrementAndGet()` | Produces sequential integers (1, 2, 3…) |
| `MathEngine.heavyScore(base, modifier)` | Calls `recursive(base, modifier, 3)` |
| `recursive` bottoms out at `depth == 0` | Builds a map with only `{100 → 2}` and calls `lookup.get(modifier)` |
| `modifier` is not `100` | `get()` returns `null` |
| `a / divisor` | Java auto-unboxes `null` Integer → **NPE** |

### 4. Why the Stacktrace Shows Wrapped Exceptions

The exception chain has **three layers** because the code manually wraps at each level:

```
CompletionException                    ← added by CompletableFuture.join()
  └─ RuntimeException: "Worker failure"  ← thrown in lambda catch block (line 33)
       └─ RuntimeException: "Score computation failed"  ← thrown in MathEngine.heavyScore()
            └─ [SUPPRESSED] NullPointerException        ← the actual root cause
```

- **`CompletionException`**: `CompletableFuture.allOf(...).join()` always wraps async task failures in a `CompletionException`.
- **`RuntimeException("Worker failure")`**: The lambda's `catch (Exception e)` block re-throws every exception wrapped, masking the original.
- **`RuntimeException("Score computation failed")`**: `heavyScore()` catches the NPE and wraps it — but crucially uses `addSuppressed()` instead of passing it as the cause, which is why it appears in a `Suppressed:` block rather than a `Caused by:` chain.

### 5. The Role of the Suppressed Exception

```java
RuntimeException wrapper = new RuntimeException("Score computation failed");
wrapper.addSuppressed(e);  // ← e is the NPE
throw wrapper;
```

`addSuppressed()` is designed for try-with-resources cleanup exceptions. Here it's misused: the NPE is the **actual cause** of the failure, but because it's suppressed rather than chained via the constructor `new RuntimeException("...", e)`, it's buried in the stacktrace under `Suppressed:` and easy to overlook. This is what makes this crash deceptively hard to diagnose.

## Suggested Fixes

**Fix 1 — Fix the lookup logic (correct the immediate bug)**

The map lookup is the wrong tool here. Replace it with a direct null-safe check or a proper default:

```java
private static int recursive(int a, int b, int depth) {
    if (depth == 0) {
        // Use b directly as divisor, guarding against zero
        if (b == 0) throw new ArithmeticException("Divisor is zero");
        return a / b;
    }
    return recursive(a + b, b, depth - 1);
}
```

Or, if the map approach is intentional, add a fallback:

```java
Integer divisor = lookup.getOrDefault(b, 1); // safe default
```

**Fix 2 — Fix the exception wrapping to use proper causal chaining**

```java
// In MathEngine.heavyScore():
catch (Exception e) {
    throw new RuntimeException("Score computation failed", e); // chain as cause, not suppressed
}

// In the lambda:
catch (Exception e) {
    throw new RuntimeException("Worker failure", e); // already done correctly here
}
```

This ensures `getCause()` traversal and logging tools expose the full chain without burying the root cause in a suppressed block.

## Additional Concurrency & Design Issues

**1. `CacheLayer` has a race condition (`HashMap` + unsynchronized write)**

```java
private static final Map<Integer, User> CACHE = new HashMap<>();
```

Multiple threads call `getUser()` concurrently without synchronization. `HashMap` is not thread-safe — concurrent puts can corrupt its internal state. Fix: use `ConcurrentHashMap` and `computeIfAbsent()`:

```java
private static final Map<Integer, User> CACHE = new ConcurrentHashMap<>();

public static User getUser(int id) {
    return CACHE.computeIfAbsent(id, Database::loadUser);
}
```

**2. `ScoreService.GLOBAL_COUNTER` grows unboundedly**

The `AtomicInteger` counter increments forever across all 50 tasks, meaning `modifier` values are always 1–50 (never `100`), which guarantees the bug triggers every single run. Even if the lookup were fixed to handle a range, an ever-growing modifier is a design smell.

**3. Unnecessary serialization round-trip**

`Serializer.serialize()` + `deserialize()` is used just to pass a `User` object — which is already in memory — to `ScoreService`. This adds CPU and memory overhead with no benefit. If the goal is defensive copying, a simple copy constructor on `User` is far cheaper.

**4. Exception wrapping obscures diagnostics**

As noted above, using `addSuppressed()` for the causal exception (rather than passing it as the `cause` argument to the `RuntimeException` constructor) makes automated error monitoring tools (like Sentry or Splunk) likely to miss the root cause entirely.
